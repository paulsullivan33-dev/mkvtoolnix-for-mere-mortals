# Writing criteria for this guide

Every "for Mere Mortals" guide is written to the same nine-point
standard, so a reader who trusts one can trust the rest. Here it
is, with the verification notes for this particular guide below.

1. **Fix it first.** Reader outcomes lead, not action items: each
   chapter opens by naming the outcome it delivers, shows a check
   the reader can run to confirm they got it, and a reasonable
   reader finishes able to state what was done, what it means,
   and what to try next.
2. **Plain language.** Short sentences, everyday vocabulary,
   technical terms defined on first use. No slang, and no
   idioms that only make sense in one country — the reader may
   be translating as they go.
3. **No dead ends.** A guide never tells the reader to do
   something it cannot show them how to verify. Every claim a
   reader relies on — an install, a command, an output — is
   something this guide demonstrates or clearly labels
   documented-only below.
4. **Live-verified where it matters.** Procedures are run for
   real in the guide's lab wherever the build machine allows it,
   and the transcripts kept in the repository are the evidence.
   What could not be run is listed honestly below, never
   presented as if it had been.
5. **General audiences.** Nothing in this guide — examples,
   fixtures, names, addresses — is modelled on any particular
   reader or author's real life, network, or organisations.
   The lab's film is synthetic: a test pattern, two tones and
   stock subtitle lines about an invented lighthouse.
6. **Standalone.** A reader needs this guide, its lab, and
   nothing else. Where another guide would genuinely help, it
   is pointed to once, by name, and the chapter still completes
   without it.
7. **Honest about limits.** Chapter 12 names what the tool
   cannot do: it never re-encodes, so contents can never be
   fixed or shrunk by it; appending refuses files whose tracks
   and codecs do not match; splits land on keyframes and a
   part's declared duration can be stretched by a straddling
   subtitle cue, so a rejoined file measured 16.03 s against
   the original 12.03 s; labels and tags are inherited from
   sources unchecked; extracted tracks lose their labels; and
   the readers exit 0 on a truncated file that holds 4 of its
   120 frames, so completeness must be measured, not assumed.
8. **The ethics rule is in the text, early.** MKVToolNix
   rearranges media — it has no means to decrypt or unlock
   protected files, and the README and chapter 1 state that
   line plainly: work on media you have the right to
   rearrange. Its own privacy edge is metadata: chapter 9
   shows, before any recipe depends on it, that titles, tags,
   encoder stamps and statistics travel with a file, and how
   to read them before sharing one.
9. **Builds clean.** The site builds with MkDocs in strict mode
   with no warnings, and a fresh reader following the chapters
   in order reaches the stated outcome of each.

## Verification notes for this guide

The build machine is a small Ubuntu 24.04 sandbox, shared with
other work while the lab ran. **MKVToolNix 82.0** (the four
tools all report "mkvmerge v82.0 ('I'm The President')" and
their siblings likewise; Debian/Ubuntu package
**82.0-1build2**, installed with `apt-get install
mkvtoolnix`) was run unmodified, entirely from the command
line. The sample media was generated by **ffmpeg 8.1.2**
(`make-fixtures.sh` in the lab folder): a 12-second 320×240
test-pattern video (H.264, keyframe every 2.5 s), two AAC
sine tones (440 Hz and 220 Hz) and a 64×96 flat-colour PNG,
plus three invented subtitle cues. ffmpeg and ffprobe also
serve throughout as the independent second witness. The
lab's measuring script is `mkvtoolnix-lab/track-table.py`,
a thin reader over `mkvmerge -J`. All transcripts live in
`mkvtoolnix-lab/transcripts/`.

Run for real, with transcripts as evidence:

- Versions of all four tools, the dpkg package version, the
  fixture build, and ffprobe/`file` descriptions of every
  fixture (t00).
- The first merge: video + two audio + SRT into one MKV with
  file title, track names and languages — 497,667 bytes,
  00:00:12.03, four tracks confirmed by both
  `mkvinfo --summary` and ffprobe (t01).
- Reading: the full mkvinfo tree (68 lines), the line-count
  contrast with `-v` (1,607), `mkvmerge --identify`, the
  JSON identification, and the lab script's track table
  showing all four tracks flagged default (t02).
- mkvpropedit in place: file title changed, video language
  set, commentary and subtitle default flags cleared, a
  track renamed, then the subtitle's forced flag set in a
  second edit — each verified by the track table and
  ffprobe, duration unchanged (t03).
- Splitting by duration (parts declared 7.5 / 6.5 / 2.03 s,
  the stretch traced by per-stream probe to the straddling
  subtitle cues) and by size (200 KB chunks); appending the
  three parts with `+` and measuring the rejoined file at
  00:00:16.03 against the original's 12.03 (t04).
- Extracting tracks 0, 1 and 3: the video counted at
  exactly 120 frames (12 s × 10 fps), the AAC probed whole,
  and the subtitle diffed against its source — identical
  cues and text, differing by a UTF-8 byte order mark and a
  trailing blank line that mkvextract adds (t05).
- The inherited tags of the plain merge (sources' ENCODER
  stamps and mkvmerge's per-track statistics tags);
  chapters, global tags and a poster attachment added with
  mkvpropedit, then extracted back: chapter marks and tag
  values exact, the attachment's md5 identical on both
  sides (t06).
- Failures, all recorded verbatim: a missing input file,
  mkvinfo on an MP4, a nonexistent extraction track ID, an
  mkvpropedit selector matching nothing (file untouched, as
  its message promises), an H.264+VP9 append refused for
  mismatched formats, the missing `+` producing an 8-track
  side-by-side file, and a 30,000-byte truncation that
  mkvinfo and mkvextract both passed with exit 0 while the
  extracted video held 4 of 120 frames (t07).
- The recipes' two merges: a second subtitle track added
  to the finished file (4 tracks to 5), and the commentary
  removed by track selection (4 tracks to 3) (t08).

Documented only — described from the project's documentation,
not run, and the text does not claim otherwise:

- **mkvtoolnix-gui**: the graphical program (its own apt
  package, also 82.0 — the package listing was read, the
  program was not installed). The lab machine is headless
  and has no display, so nothing GUI was clicked, captured
  or graded; chapter 11 characterises it only.
- Input formats beyond the ones exercised (MP4, M4A, SRT,
  WebM and MKV itself), output in WebM mode, the remaining
  split modes (timestamps lists, chapters, frames), and
  mkvextract's timecode and cue extraction modes.
- The neighbour tools of chapter 11 (HandBrake, VLC,
  Avidemux, MP4Box) — characterised, not run; ffmpeg was run
  only as fixture-maker and prober, never as a converter
  benchmark.
- Playback itself: which track a given player chooses and
  how chapters or posters render are described as the
  file's stated intent, never as an observed screening —
  the lab has no screen, and the guide's claims about its
  files stop at measurement.

Fixtures are this guide's own and deliberately generic: an
invented film title, an invented director ("A. Sample"),
stock sentences about a lighthouse keeper, tones instead of
music, a test pattern instead of footage. Nothing was
recorded, ripped or decrypted; no protected file was
involved at any point.
